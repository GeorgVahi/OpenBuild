## 1. Outcome

### Problem

Текущий контракт останавливает milestone после failed/partial writer handoff и не разрешает замену writer после инфраструктурной ошибки или timeout. Это предохраняет shared checkout, но пользователю трудно отличить корректную паузу от необратимой остановки, а путь к безопасному продолжению не оформлен отдельным протоколом.

`agent_runner.py wait` возвращает `status: "timeout"` и код `3`, пока worker может оставаться живым. Сам по себе такой timeout не является terminal result. Отдельного модуля или публичного контракта с именем `auto-patcher` в репозитории не подтверждено; этот термин пока нельзя считать владельцем поведения.

### Desired behavior

После timeout или terminal failed writer OpenBuild должен давать точную причину, состояние процесса и доступный безопасный следующий шаг. Пользователь выбрал opt-in recovery checkpoint: новый recovery milestone предлагается только после terminal evidence, подтверждённой остановки всех процессов и root-проверки сохранённого рабочего состояния; failed/partial result не становится accepted handoff. Для Direct/low-risk работы маршрут сначала повышает reasoning на той же модели, затем переходит к следующей: Luna/medium → Luna/xhigh → Terra/medium → Terra/xhigh → evidence-gated Sol/high. Medium/high начинают с Terra/medium и проходят Terra/xhigh → evidence-gated Sol/high; critical начинает с Sol/xhigh. Sol не становится стартовым маршрутом для non-critical работы; любое повышение требует доказанной нехватки предыдущей ступени, а не таймаута, транспортной ошибки или одного числового review score.

### In scope

- Уточнить семантику soft timeout, terminal timeout и route blocker.
- Спроектировать выбранный opt-in recovery-path после доказанно остановленного failed writer.
- Сохранить наблюдаемый audit trail, single-writer ownership, TDD/validation и rollback-путь.
- Добавить контрактные тесты для выбранного recovery-path и обновить русскую/английскую документацию при будущей реализации.
- Скорректировать packaged model defaults в постепенную reasoning-first лестницу для non-critical маршрутов: сначала `medium`, затем `xhigh` на той же модели, только затем следующая модель; каждая новая пара model/effort должна быть подтверждена точным runner smoke до релиза.

### Out of scope

- Принятие failed или partial handoff как успешного.
- Освобождение lease, запуск replacement writer либо запись в checkout, пока хотя бы один процесс исходного run жив или его состояние неизвестно.
- Молчаливая смена модели, tier, sandbox или provider после инфраструктурной ошибки.
- Любая реализация или адаптер внешнего auto-patcher без подтверждённой точки интеграции в OpenBuild.
- Несвязанные изменения кода, конфигурации, версий или публикаций вне данного recovery/routing update.

### Gap

The repository has strong rules that prevent unsafe continuation, but it lacks a user-visible, narrowly bounded recovery contract that distinguishes: (a) still-running parent wait timeout, (b) cancelled and proven-stopped run without writes, and (c) failed writer that may have changed files.

## 4. User scenarios

### Primary scenario — soft wait timeout

1. Parent `wait --soft-timeout-exit-zero` reaches 45 seconds while the worker/Codex process remains live and returns the same receipt with `status: "timeout"` and CLI exit zero.
2. OpenBuild repeats bounded observation of that same run for 90 and then 120 seconds; it neither releases the lease, changes model nor starts another writer.
3. After the third observation OpenBuild reports current status. Only explicit continued polling or cancellation policy follows; an observation timeout never cancels automatically.
4. Only an explicit cancellation plus confirmed process-tree stop can lead to a terminal failure and the selected recovery decision.

### Primary scenario — failed writer after partial work

1. A writer terminates with invalid/failed terminal evidence after possibly editing the workspace.
2. OpenBuild records the failed terminal receipt and never emits `implementation-handoff-accepted`.
3. The root offers the user an opt-in recovery checkpoint; after its validation it may start a new, separately identified milestone under one writer lease.

### Errors and edge cases

- Process liveness is unknown -> no lease release or replacement.
- Cancellation cannot prove every process stopped -> no recovery checkpoint.
- Dirty files overlap a failed writer’s allowed file set -> recovery requires an explicit safe disposition; never overwrite user work.
- External auto-patcher error has no mapped owner -> classify and report it; do not invent a fallback.
- A replacement candidate would change model/tier/provider because of a transport failure -> reject it.
- A non-critical writer or reviewer would move to Sol without configured evidence -> reject it; reviewer score alone is insufficient.

Supported rollback keeps the 2.2 registry guard in compatibility mode; downgrade below reader floor `2.2.0` is refused until exact vacancy, completed outbox/archive, guardian close and explicit epoch-rotating registry retirement. Unknown versions/collisions have no implicit migration; migration/GC/retirement require the workspace lock and exact vacancy.

### Security and privacy

Build-facing receipts/diagnostics must not expose prompts, private run dirs, PIDs, guardian/IPC/Job/cgroup identities, handles/secrets, artifacts, raw paths/refs/symlinks, unkeyed content hashes, maps, `checkpoint_key`, `authorization_nonce`, usage or credentials. The two secrets are independently generated and domain-separated; public content equality uses T-021 checkpoint-keyed HMAC only. Raw runner receipts remain outside scope. Private state/IPC is owner-restricted and never committed; only registry/outbox binds lifecycle/event identity.

### Performance and concurrency

Progressive 45, 90 and 120 second observations reuse one run, process identity, lease and route; they cannot spawn duplicates and do not cancel after the third window. Guardian owns provider control across reload. Before containment commit, source failure enters T-032 teardown/fallback; at/after commit guardian/provider loss quarantines regardless of prompt. The same normal lease serializes provisional teardown, one fallback claim/process/activation and terminalization; unknown state never creates replacement. Starts/migration/GC/lifecycle/outbox serialize under exact vacancy. T-026 bounds capability; no unlocked overlap.
